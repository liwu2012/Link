## 1. 背景与目标

### 1.1 背景

现有“血缘”插件工程已具备活字格插件的基础骨架：

- 单元格类型：`XyLinkCellType`（设计器中可拖拽，运行时有 JS 渲染入口）
- 客户端命令：`XyLinkCommand`
- 服务端命令：`XyLinkServerCommand`
- 服务端中间件：`XyLinkMiddleware` / `XyLinkMiddlewareInjector`
- 打包工具：`PackageTools`

当前代码仅为示例（`MyProperty`、字符串输出），尚未建立质量追溯的数据模型、查询引擎和图形化界面。

### 1.2 目标

构建一个**以批次为核心**的质量血缘图，实现：

1. **正查（向下游）**：输入产品批号 → 产品入库 → 生产订单 → 生产领料 → 原料批号 → 原料采购入库 → 供应商 / 日期。
2. **反查（向上游）**：输入原料批号 → 生产领料 → 生产订单 → 产品入库 → 产品批号，得到“该原料被用在了哪些产品上”。
3. **全链查询（双向）**：给定任意批次或单据，展示其所在的完整血缘子图。
4. **全局查询（可选）**：不输入批次，按日期、供应商、产品等条件浏览全部血缘网络（受节点上限与分页约束）。
5. **炫酷可视化**：类分子结构 / 区块链网络的血缘图，支持缩放、拖拽、路径高亮、节点详情、展开/收起。
6. **数据导出**：节点表、关系表、链路明细、图片，支持 CSV / Excel / PNG / JSON。
7. **MCP 集成**：同一套查询能力可发布为活字格 MCP 工具，让 AI 应用按自然语言调用正查/反查。

### 1.3 非目标

- 不做质量判定、检验结论生成、不合格品处置流程。
- 不修改产品入库、领料、采购等业务单据数据（只读）。
- 不做精确的“数量分摊”追溯（除非业务表中存在单件/序列号级数据）。
- 不替代现有 ERP / MES，血缘图只做关系呈现与查询。

## 2. 术语

| 术语 | 说明 |
| --- | --- |
| 产品批号 | 产成品批次标识。建议全局唯一；若不唯一，使用“产品编码 + 产品批号”作为复合键 |
| 原料批号 | 原材料批次标识。建议使用“物料编码 + 批号”作为复合键，避免不同物料批号重号 |
| 节点 Node | 图中的一个实体：批次、单据、订单、供应商 |
| 边 Edge | 两个实体之间的关系，如“生产领料”“采购入库” |
| 正查 Forward | 从产品批号向原料/供应商方向追溯 |
| 反查 Backward | 从原料批号向产品批号方向追溯 |
| 全链 Full | 同时向上游和下游扩展，得到完整连通子图 |
| 深度 Depth | 从种子节点出发经过的边数 |
| 种子节点 Seed | 查询起点（产品批号 / 原料批号 / 单据号） |

## 4. 用户场景与验收口径

### US-01 正查：产品批号追溯到原料和供应商

> 质量工程师输入产品批号 `P20261101-001`，系统展示：
> 产品批号 → 产品入库单 → 生产订单 → 生产领料单（多条）→ 原料批号（多个）→ 采购入库单 → 供应商、采购日期、来料日期。

**验收**：7 类节点完整出现；任一原料批号能展开到供应商；日期、数量、单号可见；与 SQL 基准结果一致。

### US-02 反查：原料批号查询流向产品

> 采购/质量人员输入原料批号 `M20261020-007`，系统展示所有使用该原料的生产订单、产品入库、产品批号。

**验收**：返回全部关联产品批号，不遗漏、不重复；支持按日期和产品筛选。

### US-03 全链：给定任意节点查看完整链路

> 输入生产订单号或入库单号，系统向上下游同时展开，展示完整连通子图。

**验收**：同一个连通分量中的节点全部出现（在深度和节点上限内），无孤立分支。

### US-04 导出

> 点击导出，得到 `血缘_P20261101-001_20261105.csv` 与 PNG 图片；Excel 打开中文不乱码。

**验收**：节点数、关系数与界面一致；字段完整；文件名含批号与日期。

### US-05 AI/MCP 查询

> 外部 AI 通过 MCP 调用 `lineage_backward_trace`，传入原料批号，返回 JSON，并以自然语言总结“该原料用于 3 个产品批次”。

**验收**：MCP 工具返回结构与页面查询一致；OAuth 鉴权有效；只读、无副作用。

### 5.3 节点标识规则（重要）

批号可能在不同物料间重复，**禁止只用批号做全局主键**。建议：

```
节点 ID = 实体类型 + ":" + 复合业务键
产品批号节点：productBatch:{产品编码}|{产品批号}
原料批号节点：materialBatch:{物料编码}|{原料批号}
单据节点：productInbound:{入库单号}
生产订单：order:{生产订单号}
供应商：supplier:{供应商编码}
```

展示时仍以批号为主标题，产品/物料编码为副标题。若确认批号全局唯一，可简化为 `productBatch:{批号}`。

### 5.4 索引与数据质量

**必须建立索引**（在活字格表设计器或数据库层）：

- 产品入库：`产品批号`、`生产订单号`
- 生产订单：`生产订单号`
- 生产领料：`生产订单号`、`原料批号`、`物料编码`
- 原料批号：`原料批号`、`物料编码`、`采购入库单号`
- 原料采购入库：`采购入库单号`、`供应商编码`、`批号`
- 供应商：`供应商编码`

**数据质量规则**：

1. 批号必填；不允许空批号进入血缘图。
2. 产品批号 + 产品编码 唯一；原料批号 + 物料编码 唯一。
3. 外键必须可解析；缺失时保留节点并标记 `missing` 警告，不中断整图。
4. 同一对节点间可存在多条业务关系（多次领料），边按业务单据去重，不合并数量。
5. 时间倒挂（领料日期晚于入库日期）只告警，不阻断查询。

## 6. 总体架构

```mermaid
flowchart LR
  A[活字格页面<br/>血缘图单元格] -->|输入批号/模式/深度| B[JS 渲染层<br/>XyLinkLineage.js]
  B -->|executeServerCommand| C[服务端命令<br/>血缘_查询]
  C --> D[LineageEngine<br/>正查/反查/全链]
  D --> E[IDataAccess<br/>OData / SQL]
  E --> F[(活字格数据表<br/>产品入库/订单/领料/批次/采购/供应商)]
  D --> G[图数据 JSON<br/>nodes + edges]
  G --> B
  B --> H[ECharts 血缘图渲染]
  B --> I[导出 CSV/PNG]
  C -->|发布为 MCP 工具| J[/api/mcp<br/>AI 客户端]
```

### 6.1 职责划分

| 层 | 职责 |
| --- | --- |
| 单元格类型（C# 设计器） | 设计器属性面板、默认样式、预览 |
| 单元格 JS | 工具栏、交互、调用服务端命令、ECharts 渲染、导出 |
| 服务端命令（C#） | 参数校验、权限、图遍历、组装 JSON、错误处理 |
| LineageEngine | 与 UI 无关的纯查询引擎，可被服务端命令和中间件/MCP 复用 |
| 数据访问层 | 通过 `IApplicationInformationService.GetDataAccess(context)` 读写表；复杂场景用 `ExecuteSqlAsync` 参数化查询 |
| 中间件（可选） | 为外部系统提供 `/xylineage/trace` HTTP 接口；不替代服务端命令 |

### 6.2 为什么走“服务端命令 + JS 调用”

- 服务端命令可直接使用活字格数据访问对象，权限随当前登录用户，避免前端直连数据库。
- 前端通过 `Forguncy.CommandHelper.executeServerCommand(name, params)` 调用，返回 Promise，适合图表异步加载。
- 同一条服务端命令可被活字格页面、计划任务、MCP 复用，避免逻辑分叉。
- 中间件方案适合对外 API，但需要额外处理鉴权与路由，作为 P1/P2 补充。

### 6.3 部署形态

- 插件继续打包为 `XyLink.dll`，`PluginConfig.json` 注册：
  - `assembly`: `XyLink.dll`
  - `javascript`: `Resources/echarts.min.js`、`Resources/XyLinkLineage.js`
  - `css`: `Resources/XyLinkLineage.css`
- ECharts 必须**随插件离线打包**，不依赖 CDN，适配内网部署。
- 若应用中已存在 ECharts，使用独立构建/U MD 封装，避免覆盖全局 `window.echarts`。
- 设计器属性改动后需重启设计器；运行时升级插件后需重启活字格服务。

## 7. 接口设计

### 7.1 服务端命令参数

命令名称建议：`血缘_查询`（用户在设计器中创建该服务端命令，并放入插件的“血缘查询”命令）。

| 参数 | 类型 | 默认值 | 说明 |
| --- | --- | --- | --- |
| Mode | 文本/枚举 | full | forward / backward / full / global |
| BatchNo | 文本（公式） | 空 | 种子批号；global 模式可空 |
| EntityType | 文本 | auto | auto / productBatch / materialBatch / order / inbound |
| ProductCode | 文本 | 空 | 批号不唯一时用于定位 |
| MaterialCode | 文本 | 空 | 原料复合键定位 |
| Depth | 整数 | 6 | 1–10，超过 10 截断 |
| MaxNodes | 整数 | 800 | 1–2000，保护浏览器与服务端 |
| DateFrom | 日期 | 空 | 过滤入库/领料/采购日期 |
| DateTo | 日期 | 空 | 同上 |

## 8. 查询引擎与图算法

### 8.1 核心思路

以“实体 + 业务键”为节点，以单据关系为边，在服务端做**按层批量查询**，避免逐条 N+1 查询。

正查层次：

```
产品批号
  └─ 产品入库（产品批号 = seed）
       └─ 生产订单（订单号 = 入库.生产订单号）
            └─ 生产领料（生产订单号 = 订单.订单号）
                 └─ 原料批号（物料编码 + 原料批号）
                      └─ 原料采购入库（采购入库单号）
                           └─ 供应商（供应商编码）
```

反查层次为上述反向：

```
原料批号
  └─ 生产领料（物料编码 + 原料批号）
       └─ 生产订单（生产订单号）
            └─ 产品入库（生产订单号）
                 └─ 产品批号
```

### 8.2 BFS 伪代码

```
function trace(seed, mode, depth, maxNodes):
    visitedNodes = {seed}
    visitedEdges = {}
    frontier = [seed]
    for level in 1..depth:
        if mode == forward: next = expandDownstream(frontier)
        if mode == backward: next = expandUpstream(frontier)
        if mode == full: next = expandDownstream(frontier) + expandUpstream(frontier)
        if visitedNodes.size + next.size > maxNodes:
            truncated = true
            next = next[0 : remaining]
        add next nodes/edges to result, dedupe by node.id / edge.id
        frontier = next
        if frontier.empty: break
    return result
```

### 8.3 批量查询策略

- 每一层把 frontier 的键收集成数组，按 50 个一批查询，避免超长 URL/参数。
- OData 查询示例：

```
产品入库?$filter=(产品批号 eq 'P001' or 产品批号 eq 'P002')&$select=入库单号,产品批号,生产订单号,入库日期,入库数量
```

- 复杂多表连接/大数据量时可使用 `IDataAccess.ExecuteSqlAsync(connectionStringId, sql, parameters, timeout)`，SQL 必须参数化，禁止拼接用户输入。
- OData 方式通常更贴近活字格权限模型；SQL 方式需额外校验当前用户对表/行的权限（见第 11 节）。

### 8.4 去重与合并

- 节点去重：`type + 业务键`。
- 边去重：`来源节点 + 目标节点 + 关系类型 + 业务单据号`。
- 同一批次多次领料：保留多条边（不同领料单），可在 UI 聚合为“领料 3 次 / 合计 120kg”，但底层数据不丢。
- 批号拆分/合并：图天然表现为一对多、多对一，不做 FIFO 数量分摊。

### 8.5 截断与保护

- 默认最大深度 6，覆盖“产品 → 供应商”全链；最大 10。
- 默认节点上限 800，边上限 2000；超出则返回部分图并提示。
- 单个查询超时 10 秒；超时返回 1005。
- 检测环路（理论上血缘应为 DAG），访问已访问节点即停止，防止死循环。
- 孤岛节点（缺失采购单、缺失订单）保留并附 warning，便于发现数据质量问题。

### 8.6 缓存

- 服务端按 `用户 + 查询参数 + 配置版本` 缓存 JSON，TTL 60 秒；表数据变更时可通过 `reload()` 或清缓存策略失效。
- 前端缓存同一批号最近一次结果，模式切换时先渲染缓存，再后台刷新。
- 全局浏览模式不做长缓存。

### 9.2 视觉风格

### 9.4 图渲染实现

- 图表库：**ECharts 5.x**（Apache-2.0，可离线打包），使用 `graph` + `lines` 组合。
- 节点图形：通过 `symbol: 'path://...'` 实现六边形、圆形、菱形、圆角矩形；不同类型不同尺寸。
- 布局：
  - 层级布局：服务端返回 `stage`（到种子的层数），前端按 stage 分列，列内按父节点重心排序；同层节点纵向分布。
  - 力导向布局：ECharts `force`，适合节点较少时探索。
- 大图优化：
  - 节点 > 300 时隐藏次要标签，悬停显示；
  - 节点 > 800 时启用聚合/按类型折叠；
  - 动画粒子在 > 500 边时自动关闭；
  - `progressive` 渲染与 `animationThreshold` 限制。
- 导出 PNG：`chart.getDataURL({ pixelRatio: 2, backgroundColor: '#070B16' })`。
- 生命周期：`createContent()` 建容器；`onPageLoaded()` 首次查询；`destroy()` 调用 `chart.dispose()` 防止内存泄漏。

## 11. 权限与安全

1. **数据权限**：优先使用 `IApplicationInformationService.GetDataAccess(context)`，让查询走活字格当前用户上下文；验证行级/字段级权限是否生效。
2. **SQL 兜底**：`ExecuteSqlAsync` 可能绕过部分应用层权限，只允许在服务端、参数化、白名单表/字段下使用，并在返回前按用户角色做字段过滤。
3. **输入校验**：批号、编码做长度与字符白名单校验，防止注入；所有 SQL 参数化。
4. **只读原则**：查询命令不得执行 INSERT/UPDATE/DELETE；MCP 工具不暴露写操作。
5. **敏感数据**：采购单价、供应商联系方式默认隐藏；`IncludeSensitive` 需要管理员角色。
6. **MCP 鉴权**：OAuth 2.0 客户端，最小权限；仅授权所需服务端命令；令牌有效期与轮换。
7. **审计**：记录查询人、批号、模式、耗时、是否导出、MCP 调用来源。
8. **防刷**：服务端对同一用户查询做频率限制（如 20 次/分钟），超限返回 429 类提示。

## 12. 性能与容量

| 场景 | 目标 |
| --- | --- |
| 典型单批（约 100–300 节点） | 首屏 ≤ 1.5 秒 |
| 复杂批（约 800 节点） | ≤ 3 秒，超出提示截断 |
| 反查热门原料（关联数百订单） | ≤ 3 秒，建议默认深度 4 并分页 |
| 全局浏览 | 必须分页/聚合，不允许一次性拉全表 |

优化手段：

- 数据库索引（见 5.4）。
- 按层批量查询，批大小 50。
- 服务端只返回图所需字段（`$select`），不返回整行。
- 服务端缓存 60 秒；前端缓存最近查询。
- 节点/边上限、深度上限、超时保护。
- 大图关闭粒子动画与阴影，使用简化节点。
- 避免在页面加载时查询：仅在批号有值或用户点击时触发。

### 14.2 服务端命令骨架（示意）

```csharp
public class XyLinkServerCommand : Command, ICommandExecutableInServerSideAsync
{
    [FormulaProperty] [DisplayName("查询模式")] public object Mode { get; set; }
    [FormulaProperty] [DisplayName("批号")] public object BatchNo { get; set; }
    [FormulaProperty] [DisplayName("深度")] public object Depth { get; set; }
    [ResultToProperty] [DisplayName("血缘数据")] public string ResultTo { get; set; } = "血缘数据";

    public async Task<ExecuteResult> ExecuteAsync(IServerCommandExecuteContext dataContext)
    {
        var mode = (await dataContext.EvaluateFormulaAsync(Mode))?.ToString() ?? "full";
        var batchNo = (await dataContext.EvaluateFormulaAsync(BatchNo))?.ToString();
        var depth = int.TryParse((await dataContext.EvaluateFormulaAsync(Depth))?.ToString(), out var d) ? d : 6;

        if (string.IsNullOrWhiteSpace(batchNo))
            return new ExecuteResult { errorCode = 1001, errorMessage = "批号不能为空" };

        // 关键验证点：按所用活字格版本获取数据访问对象
        var appService = dataContext.ServiceProvider.GetService<IApplicationInformationService>();
        var dataAccess = appService.GetDataAccess(/* 当前请求上下文 HttpContext */);

        var engine = new LineageEngine(dataAccess, LineageConfig.Load());
        var graph = await engine.TraceAsync(mode, batchNo, depth, maxNodes: 800);

        dataContext.Parameters[ResultTo] = JsonSerializer.Serialize(graph);
        return new ExecuteResult();
    }
}
```

> `GetDataAccess` 的上下文参数在中间件中为 `HttpContext`；在服务端命令中需按实际安装版本的 `IServerCommandExecuteContext` 获取（用官方 MCP/文档核对），这是 M0 阶段第一个验证点。

## 17. 风险与待确认问题

| 编号 | 风险/问题 | 影响 | 建议 |
| --- | --- | --- | --- |
| Q-01 | 实际表名、字段名未知 | 无法直接对接 | M0 提供表结构截图/样本数据，或接入应用后由 MCP 读取 |
| Q-02 | 原料批号是否全局唯一 | 可能串数据 | 采用“物料编码 + 批号”复合键（本方案默认） |

| Q-06 | 数据量与热门原料关联数 | 性能与可读性 | 默认深度 4 + 分页/聚合；上限可配置 |

| Q-09 | 导出格式偏好 | 影响实现 | 默认 CSV+PNG，Excel 作为 P1 |

| Q-11 | 是否需要“按数量分摊” | 追溯精度期望 | 明确当前只能做批次级关联，非单件级 |
| Q-12 | 历史数据批号缺失/格式不一 | 图断裂 | 提供数据质量报告与清洗建议，不自动改数据 |

### 18.1 正查 SQL 示例（表名/字段按实际替换）

```sql
-- 1. 产品批号 -> 产品入库
SELECT 入库单号, 产品编码, 产品批号, 生产订单号, 入库日期, 入库数量
FROM 产品入库
WHERE 产品批号 = @batchNo;

-- 2. 生产订单
SELECT 生产订单号, 产品编码, 产品名称, 开工日期, 完工日期
FROM 生产订单
WHERE 生产订单号 IN (/* 上一步订单号集合 */);

-- 3. 生产领料
SELECT 领料单号, 生产订单号, 物料编码, 物料名称, 原料批号, 领用数量, 领料日期
FROM 生产领料
WHERE 生产订单号 IN (/* 订单号集合 */);

-- 4. 原料批号 + 采购入库 + 供应商
SELECT b.原料批号, b.物料编码, b.物料名称, b.供应商编码, b.采购入库单号,
       p.入库日期, p.供应商名称, s.供应商名称 AS 供应商主档名称
FROM 原料批号 b
LEFT JOIN 原料采购入库 p ON b.采购入库单号 = p.采购入库单号
LEFT JOIN 供应商 s ON b.供应商编码 = s.供应商编码
WHERE b.原料批号 IN (/* 批号集合 */);
```
